# المرجع: كيف تحكم المنصّة على ما يحدث في الريبو

كل سيناريو هنا **ريبو git حقيقي** يُبنى في مجلد مؤقت: كوميتات، وفروع، ودمج، وrebase،
وcherry-pick. ثم يُحوَّل كل push فيه إلى ما يرسله GitHub فعلاً، ويمرّ على **كود
الإنتاج نفسه**: `normalizePush`، ثم الإثراء، ثم `weighPush`، ثم `evaluateRules`. وفي
الآخر يُقارَن الحكم بما يجب أن يكون.

لا شبكة، ولا قاعدة بيانات، ولا نموذج لغوي. الحكم هنا حسابٌ على ريبو، ويُعاد حرفياً في
كل تشغيل، فالهويات والأوقات ثابتة والـ sha نفسه في كل مرة.

## كيف يُقرأ سيناريو

```ts
{
  id: "squash-merge",
  title: "PR squash-merged: one new commit carrying the whole branch",
  story: async (story) => { … },          // التاريخ: من فعل ماذا، وبأي ترتيب
  expect: CLEAN,                           // ما يحكم به مراجعٌ يُعتمد عليه
  defect: {                                // اختياري: ما يحكم به الكود اليوم حين يخالف
    observed: charged("large_diff@omar"),
    because: "…",                          // لماذا، والسطر المسؤول، وبند المقترح
  },
}
```

- **الحكم** يُكتب `rule@login`: القاعدة، ومن سيُكتب عليه في السجل. الشخص نصف الحكم،
  فتهمةٌ صحيحة على الشخص الخطأ حكمٌ خاطئ.
- **`expect` سياسة لا مخرَج.** هو ما يجب أن يكون، ويُكتب قبل أن يُنظر فيما يفعله
  الكود. تغييره قرارٌ يُكتب سببه.
- الحكم المختبَر هو حكم **آخر حدث** في القصة. ما قبله تمهيد، ويظهر كاملاً في رسالة
  الفشل (`trail`).

## قاعدة العيب المعروف

العيب المسجَّل عقدٌ صارم في الاتجاهين:

| ما يحدث | النتيجة |
|---|---|
| الكود ما زال يحكم كما سُجّل في `observed` | ينجح. العيب معروف ومكتوب |
| الكود صار يحكم بـ `expect` | **يفشل**: احذف سجلّ العيب. مرجعٌ يَذكر عيباً أُصلح يكذب |
| الكود صار يحكم بشيء ثالث | **يفشل**: حدّث `observed` إن كان تقدّماً، وإلا فهو تراجع |

فالقائمة تنقص ولا تتغيّر بصمت، وأي تطوير يمسّ الحكم ينعكس هنا في الحال. لتعرف ما بقي
من العيوب: `grep -n "defect:" apps/api/src/scenarios/*.test.ts`.

## ما الذي تفترضه السيناريوهات

- **ما يرسله GitHub** محسوبٌ في [`github.test.kit.ts`](github.test.kit.ts)، ورأسه جدولٌ
  بكل افتراض ومصدره: سقف الكوميتات، و`distinct`، وصفحة الملفات، وحقل
  `previous_filename`. الافتراض الخاطئ يُصحَّح هناك في سطر.
- **ترتيب خطوات المعالج** منقول في [`judge.test.kit.ts`](judge.test.kit.ts)، وكل خطوة
  تذكر الملف الذي نقلتها منه. إن تغيّر ترتيب `delivery.processor.ts` أو بواباته فهذا
  الملف يتبعه. وحين يصير القرار دالة نقية
  ([0009 §1](../../../../docs/proposals/0009-judging-what-happened.md)) يستدعيها
  المرجع مباشرةً ويسقط هذا النقل.
- **الجبهة الافتراضية** تراقب كل الفروع، والـ App مثبّت، والقواعد المشحونة مع تشغيل
  `large_diff` على عتبته المشحونة. وهي ليست صامتة ولها قناة، فكل دفعة يُحكم عليها
  تُسجَّل.

## كيف تضيف سيناريو

١. اختر الملف بحسب الموضوع: هبوط PR، أو الفرع الرئيسي، أو بقيّة الدمج، أو فرع العمل،
   أو طريق الوصول.
٢. اكتب القصة بأدوات [`story.test.kit.ts`](story.test.kit.ts): `seed`، و`work`،
   و`story.push`، و`story.mergePullRequest`، و`story.merge`، و`story.git.rebase`…
٣. اكتب `expect` بما يجب أن يكون، **قبل** أن تشغّله.
٤. شغّل. إن خالف الكودُ `expect` فأنت أمام أحد أمرين: عيبٍ تسجّله في `defect` مع
   سببه، أو سياسةٍ كتبتها خطأً فتصحّحها.

والحالات الغريبة هي الأثمن هنا: دمجٌ بعنوان مزوّر، وpull يُنتج merge، وfoxtrot،
وoctopus، ودفعٌ بالقوة يحذف ولا يضيف، وrename يتبعه تغيير كامل. كل شكلٍ يستطيع git
أن يعبّر عنه هو شكلٌ سيصل المنصّة يوماً.

## التشغيل

```bash
npm run build -w @commander/shared         # السيناريوهات تقرأ dist الخاص بـ shared
npm run test -w @commander/api             # مع بقية اختبارات الـ API
cd apps/api && npx tsx --test src/scenarios/pr-landing.test.ts   # ملفٌ واحد
```

يحتاج `git` على الجهاز. كل ملف يشغّل سيناريوهاته بالتوازي، والكلفة كلها في عمليات
git، فالمنصّة التي يُنشأ فيها process بثمن أقلّ تنهيه أسرع.
